# TB3386 道岔缺口监测设备设计记忆

> 对应源码：`src/io_server/ioDev_tb3386.h`、`src/io_server/ioDev_tb3386.cpp`  
> 协议文件：`TB3386 道岔缺口监测系统设备(正文).pdf`

## 1. 设备类型注册

- `devType`：`tb3386-device`
- 显示标签：`TB3386道岔缺口`
- 注册位置：`src/io_server/ioDev_tb3386.cpp` 匿名命名空间工厂

## 2. 通信模式

TB3386 下位机采用 **TCP 客户端主动上发** 模式，上位机只负责监听并解析二进制帧，无需主动轮询。因此：

- `DoAcq()` 仅记录最后一次采集时间，不发送请求。
- `DoCycleTask()` 只保留离线检测，不调用基类 TDSP 的 JSON 轮询。
- 数据帧通过 `onRecvData_tcpClt()` → `stream2pkt` 分包 → `onRecvPkt()` → `Parse315Protocol::Parse()` 处理。

## 3. 当前实现命令

仅实现 `0x26` 和 `0x24` 两个命令，其余命令（图像、配置、校时等）暂不处理。

### 3.1 0x26 缺口数值帧

帧体：`命令码(1) + 总记录数(2) + 记录 × N`

每条记录字段：

| 字段 | 长度 | 说明 |
|------|------|------|
| 采集时间 | 4 | UNIX 时间戳，低字节在前 |
| 转辙机 ID | 2 | 设备下通道编号依据 |
| 定反位 | 1 | 0 定位(fix)，1 反位(invert) |
| 偏移标志 | 1 | 0 无效，1 左偏负，2 右偏正 |
| 偏移值 | 2 | 低字节在前，÷100，单位 mm |
| 缺口值 | 2 | 低字节在前，÷100，单位 mm |
| 标准值 | 2 | 低字节在前，÷100，单位 mm |
| 缺口值类型 | 1 | 0 静态/轮询，1 操纵后，2 过车时 |
| 预留 | 3 | 0xFF |

处理逻辑：

1. 解析记录，按 `转辙机 ID` 更新内部缓存 `StZZJCache`。
2. 若缺口值的 **时间戳发生变化**，触发一次数据库写入。

### 3.2 0x24 设备状态帧

帧体：`命令码(1) + 转辙机个数(2) + 记录 × N`

每条记录字段：

| 字段 | 长度 | 说明 |
|------|------|------|
| 转辙机 ID | 2 | 低字节在前 |
| 油位 | 2 | 0xFFFF 表示未采集 |
| 油位采集时间 | 4 | UNIX 时间戳 |
| 摄像头状态 | 2 | 0 正常，1 故障，0xFF 不监测 |
| 摄像头状态时间 | 4 | UNIX 时间戳 |
| 温度 | 2 | 低字节在前，有符号，÷100，℃ |
| 温度时间 | 4 | UNIX 时间戳 |
| 湿度 | 2 | 低字节在前，÷100，% |
| 湿度时间 | 4 | UNIX 时间戳 |
| 预留 | 4 | 0xFFFFFFFF |

处理逻辑：

- 仅提取温度和湿度，更新对应转辙机缓存。
- 不触发数据库存储。

## 4. 相对绑定与位号查找

TDS 中 **相对绑定** 是重要概念：

- 一个 `ioDev*` 设备对象自身会绑定到项目中的某个父对象（位号如 `杭州站.1#`）。
- 该设备下的 `ioChannel*` 子通道，绑定的位号只是 **相对于父设备位号的相对位号**。
- 父位号 + 子通道相对位号拼接后，才是通道在项目中的完整位号。

在本设备中的用法：

1. 读取设备自身配置 `tagBind`，得到父位号（如 `杭州站.1#`）。
2. 将协议中的 `转辙机 ID` 转成字符串（如 `"1J1"` 对应 ID 为某个整数值，实际以十进制字符串匹配）。
3. 遍历所有子通道 `m_channels`，取每个通道的完整 `tagBind`。
4. 去掉父位号前缀和点号，得到 **相对位号**。
5. 相对位号与 ID 字符串相等，即找到该转辙机对应的通道完整位号。

示例：

- 设备 `tagBind`：`杭州站.1#`
- 通道 A `tagBind`：`杭州站.1#.1J1`
- 通道 A 相对位号：`1J1`
- 若协议转辙机 ID 字符串为 `1J1`，则命中通道 A。

> 注意：相对位号可以是任意字符串，不一定是数字。配置时保证通道相对位号与下位机转辙机 ID 字符串一致即可。

## 5. 数据库存储

### 5.1 存储触发条件

- 仅当 0x26 命令中某转辙机的 **缺口值时间戳发生变化** 时，才写入一次。
- 写入时读取缓存中的温度/湿度，与本次缺口值一起打包。

### 5.2 目标位号

若转辙机通道位号为 `杭州站.1#.1J1`，则数据存入：

```text
杭州站.1#.1J1.缺口
```

后缀 `.缺口` 为约定名称。

### 5.3 数据元 JSON 格式

```json
{
  "time": "2026-07-08 11:12:13",
  "gap": 2.3,
  "std": 2,
  "pos": "fix",
  "tempRail": 23.1,
  "tempZZJ": 24,
  "tempWeather": 23
}
```

字段说明：

| 字段 | 来源 | 说明 |
|------|------|------|
| time | 0x26 缺口采集时间 | 格式 `YYYY-MM-DD HH:MM:SS` |
| gap | 0x26 缺口值 | ÷100，单位 mm |
| std | 0x26 标准值 | ÷100，单位 mm |
| pos | 0x26 定反位 | 0→"fix"，其他→"invert" |
| tempZZJ | 0x24 温度 | 转辙机内温度 |
| tempRail | 0x24 温度 | 轨温（协议未提供，暂用同一温度占位） |
| tempWeather | 0x24 温度 | 天气预报温度（协议未提供，暂用同一温度占位） |

> 当 0x24 温度尚未收到时，JSON 中不包含温度字段。

### 5.4 调用接口

```cpp
DB_TIME stTime;
stTime.fromUnixTime(cache.gapTime);
db.Insert(storeTag, sDE, &stTime);
```

## 6. 内部缓存结构

`ioDev_tb3386` 内部维护 `std::map<unsigned short, StZZJCache> m_mapZZJ`：

- key：转辙机 ID
- value：该转辙机最近一次缺口、温度、湿度及各自时间戳
- 访问时加 `std::mutex` 保护

## 7. 配置要点

1. 添加设备，类型选择 `TB3386道岔缺口`。
2. 设备 `tagBind` 绑定到站点对象（如 `杭州站.1#`）。
3. 在设备下添加子通道：
   - 每个子通道对应一台转辙机。
   - 通道 `tagBind` 使用完整位号，如 `杭州站.1#.1J1`。
   - 相对位号（去掉父位号后的部分）必须与协议中的转辙机 ID 字符串一致。
4. 系统会自动在该通道位号后追加 `.缺口` 存入数据库。

## 8. 遗留与扩展

- 当前不处理图像（0x2A/0x2B）、校时、参数配置等命令。
- `tempRail`、`tempWeather` 目前用 `tempZZJ` 占位；后续若需真实轨温或天气温度，可从其他 MP 或外部接口接入后修改 `buildGapJson()`。
- 若下位机不支持主动上发，可在 `onEvent_online()` 中补充发送 0x26/0x24 查询帧。
