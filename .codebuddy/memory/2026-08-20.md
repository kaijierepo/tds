## Gitee 私人令牌认证修复（上午）

- 用户本机 git clone gitee 仓库时一直弹 `Enter basic credentials for 'https://gitee.com/'`。
- **根因（多层）**：
  1. 本机 `credential.helper` 有 system 级（`D:/Program Files/Git/etc/gitconfig`）`manager`（GCM）+ global 级 `store` 累积生效，manager 在前且其 UI 组件缺失（`warning: could not find UI helper 'git-credential-manager-ui'`）→ 退化命令行交互弹框；
  2. 用户按建议写了 `C:\Users\lutao\.git-credentials`，但 GCM(manager) 根本不读该文件（那是 store helper 的存储）；即使配置 store，**文件是 CRLF 结尾**（64 字节 = 63+CRLF），store 解析时 host 带 `\r` 匹配 `gitee.com` 失败。
- **修复（已验证 `git ls-remote` 返回 HEAD）**：
  1. 重写 `.git-credentials` 为干净格式：无 BOM、ASCII、LF-only 单行（`https://用户名:令牌@gitee.com`，用户名是手机号 18668216925，令牌 32 位）；
  2. `C:/Users/lutao/.gitconfig` 的 `[credential]` 段改为：`helper =`（空串，清除 system 的 manager）→ `helper = store`（在前，读文件）→ `helper = manager`（兜底，保 GitHub 等 GCM 凭据）。
- **关键坑**：PowerShell 传空字符串参数给 `git config ... ""` 会被丢弃（写不进去），必须用 `--unset-all` 重写或用编辑器直接改 .gitconfig 文本。
- 用户新仓库：`https://gitee.com/lutaooooo/little-octopus.git`（用户名 lutaooooo）。

## 流水线 release 附件失败：package.sh 依赖调用目录（第一轮，上午）

- **现象**：release@gitee 报 `no asset file matches glob pattern`。
- **根因**：`build.sh` 自带 `cd ../src`（自包含路径），但 `package.sh` 用 `../out/tds` 相对路径依赖调用者在 build/ 目录；Gitee Go `build@gcc` 的 commands **每行是独立 shell**，`cd build` 不持久 → `package.sh` 在仓库根运行 → 找不到产物 → `set -e` 提前退出 → **tar.gz 从未生成**。
- **修复（commit `ad8ec559`，注意 push 后 hash 被 rewrite，summary 里记的 `8e95c758` 实际是 `ad8ec559`）**：
  1. `build/package.sh`：ARCH 校验后加 `cd "$(dirname "$0")"`（自包含）；
  2. `.workflow/linux-x86_64.yml`：build 步骤 commands 合并为一行 `&&` 链（失败即停）。

## 流水线 release 附件失败：assertFiles 目录/glob 不可靠（第二轮，下午）

- **现象**：tds-30（commit `ac3f7c4f`，已含 ad8ec559 修复）仍报 `no asset file matches glob pattern: /root/workspace/liangtuSoft/tds/out/tds/tds-*.tar.gz`。三次尝试（`./tds-*.tar.gz`、`./out/tds/tds-*.tar.gz`）都失败。
- **调查结论（Gitee 官方博客 2026-01-23）**：
  - `assertFiles` 路径基于 Release 步骤工作目录（源码根目录）；`upstreamArtifact` 只负责把产物放到工作目录；
  - 目录型 artifact 下载后"通常"保留层级，但**官方从未确认 assertFiles 支持 glob 通配符**，示例全是精确文件名；
  - 官方演示标准用法：build 上传**文件**（如 `plugin-amd64`）→ release `assertFiles: plugin-amd64`（精确路径）。
- **修复（commit `c3fdf424`，已推送）**：走官方标准用法，绕开 glob 和目录层级两个不确定点：
  - build 步骤：`... && cp out/tds/tds-*.tar.gz ./tds-linux-x86_64.tar.gz && ls -la ./tds-linux-x86_64.tar.gz && find . -maxdepth 3 -name "*.tar.gz"`（固定名文件复制到工作目录根）；
  - artifacts path：`./out/tds`（目录）→ `./tds-linux-x86_64.tar.gz`（单个文件）；
  - assertFiles：`./tds-linux-x86_64.tar.gz`（精确路径，无 glob）；
  - description 同步改为 `tds-linux-x86_64.tar.gz`。
- **经验教训**：
  - Gitee Go build@gcc commands 每行独立 shell，`cd` 不跨行——脚本必须自包含路径或合并 && 链；
  - release@gitee 的 assertFiles **优先用精确文件名**，目录/glob 行为未确认；目录型 artifact 上传后下游解压层级也不能保证；
  - 调试时 build 步骤最后加 `find . -maxdepth 3 -name "*.tar.gz"` 输出便于定位；
  - PowerShell 里 `git commit -m` 含内嵌双引号会被拆坏，message 避免内嵌引号。
- 待验证：重跑流水线确认 release 能挂上附件。
- **用户疑问澄清（重要）**：用户曾认为"release 创建成功 = 只改 assertFiles(53行) 即可"，**这是错的**。assertFiles 路径必须在 release 工作目录真实存在，内容来自 upstreamArtifact 下载解压，而下载内容取决于 build 步骤 artifacts.path 上传了什么——必须三处联动（build 命令 cp 固定名 → artifacts 上传该文件 → assertFiles 精确路径）。只改一处必然报 no asset file matches。用户曾把 yml 回退为旧版，已重新应用修复并确认工作区与 HEAD(c3fdf424) 一致。
- **release 阶段改手动触发（commit `e600fb72`）**：用户需求"每次提交都编译但不每次发版"，方案是 Gitee Go 的 build 与 release 本就是独立阶段——build 保持 `trigger: auto`（每次 push 自动编译，BUILD_ARTIFACT 保留在流水线可下载），release 阶段 `trigger: auto` → `manual`（想发版才手动点）。已推送。**无需自建 CICD**（Jenkins/Gitea Actions 过度工程，违背极简原则）。另外提醒用户：之前失败的构建在 Gitee 留下了多个空 release（tds-23~30 无附件），需手动清理。
- **用户改主意：每次都要发版下载测试**，于是把 release 阶段改回 `trigger: auto`（commit `a6ed23bd`）。
- **最终方案（commit `11cdec7d`）**：
  - tag/releaseName 固定为 `tds-latest-linux-x86_64`（每次 push 覆盖同一 release/tag，避免 tag 无限堆积）；
  - 附件文件名改为 `tds-v{提交次数}-linux-x86_64-{yyyyMMdd_HHmmss}.tar.gz`（用户在图片中给出的格式）；
  - 实现方式：`package.sh` 里 `VER="tds-v${REV_COUNT}-linux-${ARCH}-$(date +%Y%m%d_%H%M%S)"`；build 步骤把 `out/tds/tds-v*.tar.gz` 复制到工作目录根；artifacts path 和 assertFiles 都用 `./tds-v*.tar.gz`（依赖 release@gitee 的 glob 支持，但文件型 artifact 在根目录下 glob 应该可匹配）。
- **关键权衡**：要动态附件名就必须用 glob/变量；Gitee 官方未确认 assertFiles glob 支持，但这是实现动态文件名的唯一可行路径。若失败，再考虑
